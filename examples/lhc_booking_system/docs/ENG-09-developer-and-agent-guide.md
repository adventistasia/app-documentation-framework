# LHC Booking System – Developer & Agent Guide

## Purpose

The first thing a developer or AI agent reads before changing the LHC Booking System. It explains where things are, the exact commands to build, run and test, the conventions to follow, how to make a change safely, what an agent may and may not do alone, and which documents to update with each kind of change. It also holds the environments, configuration, secrets and feature flags (ENG-06).

## Scope

Covers working on the code in the `lhc-booking` repository and the configuration of its environments. What the application is for is in BUS-01; how it is designed in ENG-03; deployment in ENG-07; operations in ENG-08.

## What this application is

The LHC Booking System lets guests ask for a room at the LHC guest house through a public form and follow their request through a booking link, and lets LHC front office staff review requests against live availability, confirm, return or reject them, assign rooms without double-booking, and check guests in and out. It is a Django monolith on Azure App Service with PostgreSQL, sending email through M365 and signing staff in with Entra ID. See BUS-01 for the business case and owners.

## Coding conventions and patterns

| Topic | Rule | Example to copy | Avoid |
|---|---|---|---|
| Layering | Views call domain services in `services.py`; only services and models touch the database | `lhcbooking/bookings/services.py` | Queries or rule checks in views or templates |
| Business rules | Each rule is one function in `rules.py`, named and commented with its BR ID, returning the user message from BUS-09 | `rules.check_br04_availability` | Re-implementing a rule in a second place |
| Status changes | Only through `lifecycle.transition(booking, to_status, user)`, which checks the TR table and the rules | `lhcbooking/bookings/lifecycle.py` | Setting `booking.status` directly |
| Emails | Write an outbox row with `notifications.queue(...)` inside the same transaction; never call SMTP from a view (ADR-005) | `lhcbooking/notifications/outbox.py` | `send_mail` in request code |
| Audit | Every state-changing service calls `audit.record(...)` in its transaction (FR-23) | `lhcbooking/audit/api.py` | Changes without an audit event |
| Personal data | Never log guest name, email, phone or special requests; use the booking reference | `lhcbooking/observability/filters.py` | `logger.info(booking.guest_email)` |
| Time | Use `core.clock.today()` and `now()`; never `date.today()` | `lhcbooking/core/clock.py` | Server-local time |
| Naming | Use the terms in SP-01 (Booking, Room type, Returned); code names in snake_case | | Synonyms such as "reservation" or "pending" |
| Tests | Acceptance tests are named after their AC ID and use the SP-11 test data | `tests/acceptance/test_ac_12.py` | Tests that depend on today's real date |

```python
# Guarded status transition with audit and notification in one transaction
with transaction.atomic():
    rules.check_br04_availability(booking)          # raises RuleError with the BUS-09 message
    booking.nightly_rate = rates.rate_for(booking)   # BR-10
    lifecycle.transition(booking, Status.CONFIRMED, user=request.user)  # TR-05
    notifications.queue("NTF-05", booking)
```

## How to make a change safely

1. Create a branch from `main` named `<type>/<short-description>`, for example `fix/audit-export-columns`.
2. Write or update tests first for the behaviour you are changing; acceptance tests reference their AC IDs from SP-11.
3. Make the change following the conventions above.
4. Update the documents listed for your kind of change in the update-trigger table below, in the same pull request.
5. Run test, lint and the documentation linter locally.
6. Open a pull request; describe the change, the documents updated and any new IDs.
7. Get review from Priya Nair, ITS Application Lead, or Leo Santos, ITS Developer; changes in "Needs a human" below need Priya Nair's approval.

**Definition of done:**

- [ ] Behaviour matches the requirement (ENG-01) and its acceptance criteria (SP-11) pass.
- [ ] Tests added or updated; the full suite passes.
- [ ] Lint and the documentation linter pass.
- [ ] Every document required by the update-trigger table is updated in the same pull request.
- [ ] Any significant technical decision has an ADR in ENG-10.
- [ ] Release notes entry written if users or administrators will notice (ENG-07).
- [ ] No personal data in new log lines.

## Agent rules

**May change without asking:**

- Code and tests within an assigned task, following the conventions above.
- Documentation updates required by the update-trigger table.
- Dependency patch versions when the full suite passes.
- Screen text that is not a status meaning, an error message in BUS-09 or a notification.

**Needs a human (stop and ask Priya Nair, ITS Application Lead):**

- Database schema changes and data migrations (ENG-04).
- Anything touching authentication, authorisation, roles or permissions (BUS-04).
- Changing a business rule, status or transition (BUS-05), including the 14-day expiry and the 10-submission rate limit.
- Changing the text of a notification, a status meaning or an error message users see (BUS-06, BUS-05, BUS-09); Daniel Reyes, LHC Front Office Supervisor, agrees the wording.
- Adding or removing an external dependency or integration (ENG-05).
- Configuration, secrets or feature flags in ENV-03 (ENG-06), including FLAG-01.
- Reversing or contradicting an Accepted ADR in ENG-10.
- Marking any document Accepted or recording any sign-off.

**Never:**

- Write a secret value into code, configuration committed to the repository, documentation, logs or a pull request.
- Invent a value, an owner, a test result or an approval in documentation; write `TBD` with an owner and a `Q-xx` instead.
- Deploy to production, run migrations against ENV-03, or read or change production data.
- Remove or weaken the `no_double_booking` exclusion constraint (ADR-002).
- Disable or skip failing tests to make a build pass.
